# Project Layout — Canonical Principles

Generic layout doctrine that holds for **any** stack. The concrete directory tree for THIS project —
exact folder names, package layout, where migrations/tests/config live — is decided once by the
spec-writer and recorded in `spec/architecture.md` (and mirrored here, under `## This Project's Layout`,
if it's non-obvious enough to be worth restating). This file is the doctrine; it is not itself the tree.

---

## README Requirements (Mandatory)

Every project **must** have a README that:

1. **States the exact working directory for every command** — if the repo root IS the project, say so
   up front; if there's a subdirectory to `cd` into, name it. Put this as a blockquote or bold warning at
   the very top, before any other content.
2. **Prefixes every command with whatever this stack's tooling requires** — a version/dependency-manager
   wrapper (`uv run`, `bundle exec`, `poetry run`, a Docker Compose wrapper, etc.) if one is needed. Bare
   commands that only work with a manually-activated environment will fail for the next person who copies
   them.
3. **Includes a verification step after any migration/setup command** — so the user can confirm the step
   actually took effect (e.g. `alembic current`, `prisma migrate status`, a health-check curl), not just
   that the command exited 0. Blank/silent success from a migration tool usually means nothing happened.
4. **Stays accurate** — every README command must be tested before a phase is marked complete. If a
   command fails, fix the README before claiming the phase is done.

The README is the first thing a user touches. A wrong README fails the entire build regardless of
whether the code works.

## Source Code Rule (Non-Negotiable)

**All application source code lives inside one clearly-named source root** — call it `src/`, `app/`,
`lib/`, or whatever this language/framework's convention is (record the actual choice in
`spec/architecture.md`). Never scatter HTML, CSS, JS, packages, templates, or data files loose at the
repo root alongside config files.

The repo root is for project-level config only: the manifest file(s) for this stack's package manager,
migration config, `README.md`, `.env.example`, and the harness/spec boilerplate (`spec/`, `harness/`,
`CLAUDE.md`). If you are about to create an application file at the root, stop and put it in the source
root instead.

This applies to every project type — a Python package, a static web app, a TypeScript monorepo, a Go
module, anything.

## Bolting the Harness Onto an Existing Codebase

When this harness is added to a project that already has real application code (the common case — most
projects importing this harness are not greenfield), **the existing layout wins.** The first
`/zero-shot-build` run must:

1. Document the codebase's actual current structure in `spec/architecture.md` (`## Stack` +
   `## This Project's Layout`) — don't invent an idealized layout that doesn't match reality.
2. Never scaffold a second, parallel source tree "the harness way" next to code that already works. New
   capabilities extend the existing structure; they don't duplicate it.
3. Adopt the existing project's own conventions for source layout, test location, and build tooling as
   the binding rules for every subsequent phase — the sections below (Directory Tree, package boundaries,
   etc.) describe the doctrine for a **greenfield** build; an existing codebase's own layout takes
   precedence whenever the two disagree.

## Directory Tree Principles (greenfield default — adapt per stack)

For a project built from scratch under this harness, the spec-writer records the concrete tree in
`spec/architecture.md`, following these principles:

- **One canonical source root.** No second package/app directory duplicating the first — if the spec
  needs a different name than the skeleton shipped with, rename in place rather than adding a sibling.
- **Tests live at a predictable, documented location** — either colocated with source (common in
  Go/Rust/JS) or in a top-level `tests/` directory (common in Python), whichever this stack's ecosystem
  convention is. Document the choice; don't mix both without a reason.
- **Config at the boundary, not scattered.** Environment/config loading lives in one module/package, not
  duplicated across the codebase.
- **Migrations (if the project has a database) live in one directory**, generated by the stack's standard
  migration tool (Alembic, Prisma Migrate, golang-migrate, ActiveRecord migrations, etc.) — never
  hand-written schema drift.
- **`spec/`, `harness/`, `CLAUDE.md` are preserved from the boilerplate** at the repo root regardless of
  stack — they are process artifacts, not application code, and coexist with whatever the source root is
  called.

## Exact File Shapes

This harness intentionally does **not** hardcode file-level code shapes (e.g. a specific settings-class
layout, a specific migration template, a specific ORM model pattern) here, because those are inherently
language/framework-specific. The spec-writer records this project's actual chosen shapes — its settings
pattern, its migration template, its error-handling pattern, its ORM/ODM conventions — in
`spec/architecture.md` and `harness/patterns/code.md`'s per-project sections, and every generator builds
against those, not against an assumption baked into this file.

## Rules

1. **Application code goes in the source root** — never in the boilerplate/root config area.
2. **No repository-pattern-by-default** — direct queries at the appropriate layer are fine unless the
   spec calls for an explicit repository/DAO layer; don't add indirection nobody asked for.
3. **Directory names match the ecosystem's own convention** for this stack — don't force a Python-shaped
   tree onto a Go project or vice versa.
4. **State/config types use whatever typed-data primitive this language offers** (TypedDict/dataclass/
   Pydantic model in Python; an interface/type in TypeScript; a struct in Go) — pick one per project and
   stay consistent.
5. **Prompts, templates, or other non-code text assets** live in a clearly-named directory, loaded at
   runtime rather than inlined as string literals scattered through the code.
6. **Any abstraction layer for an external provider** (LLM client, payment provider, etc.) is wrapped so
   the concrete SDK is never called directly from business logic — this makes swapping providers and
   testing cheap, regardless of language.
